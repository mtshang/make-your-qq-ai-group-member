# 备选协议端观察名单（非当前建议）

> **定位**：NapCat 路线**真的出问题**（频繁被风控踢下线、C9 重扫成为日常、且养号无效）时的备选调研存档。当前 NapCat 稳定就**不要动**——换协议端是部署流程大改，无谓风险。
>
> **决策原则（社区共识，实测帖反复验证）**：账号质量 > 框架选择。换端之前先按顺序排除：① C7（quick.bat 占位号没改导致每次重启扫码——那是配置问题，换什么端都没用）② 养号（少群发、常用设备+常用 IP、让号变"常用号"）③ 同号多开互踢 C5。全排除了再回来看这份名单。

## SnowLuma（观察名单第一名，唯一有"比 NapCat 更稳"实证的方案）

- **是什么**：独立 OneBot v11 协议端（TypeScript 互操作运行时），把 QQ 原生会话转成 OneBot v11 动作/事件，经 WebSocket/HTTP/WebUI/SDK/MCP 统一接入。2025-06 创建，约 1.1k star（上升期）。仓库 <https://github.com/SnowLuma/SnowLuma>
- **背景硬**：NapCat 作者参与了开发；NapCat 官方 README 推荐它作为替代品；参考了 LagrangeV2 协议定义 + NapCatQQ 实现思路
- **风控口碑**：linux.do 多条一手实测——"NapCat/LLBot 老被踢下线，换了 SnowLuma 就再没掉过"。但**样本是幸存者偏差级别，无机制保证**：风控玄学（同号同端 Windows 一小时封、Linux+Docker 稳 8 个月后突然又掉）
- **事实修正**：它**仍需接入 QQ 客户端进程**（README 原文"面向 QQ 客户端""按引导接入 QQ 进程"），不是无 QQ 纯协议实现（那是 Lagrange 路线）——风控本质上仍是"非官方客户端"同类风险
- **许可红线（关键）**：源码可见非商业许可（非 OSI）；**原生附加组件是专有闭源组件**；EULA §5.4 规定"并入第三方安装包/Docker 镜像、**通过自动化脚本部署**"须事先书面授权
  - 前车之鉴：qq-bridge（QQ↔DSH 桥接，协议端整体用 SnowLuma）为此**删掉了 start/stop 工具**，只留只读探活，安装/启动/扫码全部留给用户手动
  - **若 skill 支持 SnowLuma 的合规形态**：安装/启动/扫码三步必须留用户手动（官方流程本来就是：Release 下载发行包 → 双击 `launcher.bat` → WebUI `:5099` 初始密码登录 → 引导接入 QQ + 配 OneBot 连接），agent 只做 OneBot 反连对接、AstrBot 侧配置、验收与运维——"全自动部署"卖点在该路线不成立（NapCat 宽松开源不受此限）
- **迁移账单**：上层全复用（AstrBot/人格/插件/OneBot v11 反向 WS 概念相同）；下层全重写——Phase 6 安装组装、bot_manager 进程定位/启停（进程树形态不同需实测）、quick.bat 免扫码逻辑（SnowLuma 登录态体系不同）、fileLog 日志判读（它有 WebUI 实时日志）
- **触发迁移的判定**：NapCat 在当前环境下 2~4 周内反复被踢（≥3 次，且 C7/C5 已排除、养号已做）→ 才值得评估。评估时先实测：发行包进程树形态（ctypes 定位怎么改）、登录态文件位置、OneBot 反连配置方式、日志体系

## 其他候选（一句话档案）

- **Lagrange (LagrangeV2)**：纯协议实现、不依赖 QQ 客户端进程——理论风控面不同，但社区声量小、QQ 支持完整度存疑，未见到"更稳"实证
- **LLOneBot / LuckyLilliaBot(LLBot)**：也有"N换了不掉"的零散反馈；但 2025 年中社区传 LLBOT 停更/跑路，活跃度存疑，不推荐作为目标
- **腾讯官方 QQ 机器人（q.qq.com）**：**风控问题的一劳永逸解**——官方审核秒过、无封号风险、支持 Markdown 消息；但能力受限（群聊场景/接口权限有官方约束），且不是本 skill 的"自己的号自己部署"形态。**如果 bot 号反复被风控，注册官方 bot 是比换任何协议端都稳的退路**，值得知道它存在
